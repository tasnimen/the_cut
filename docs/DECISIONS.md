| Why Cloudinary replaced ImgBB | Owner decision 2026-10-30 | ImgBB was blocked for the owner (provider error code 103), so no upload could ever work. Cloudinary has a free plan, signed server-side uploads, deletes by public id (no secret delete links stored), and a stable CDN. Cost of the switch: a new account and three variables (`CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET`). ImgBB images that already exist stay renderable (the `i.ibb.co` remote pattern and CSP entry stay while such records exist; delete them from the database and remove both entries to retire it) and can still be deleted if `IMGBB_API_KEY` is kept. |
| Image delivery loader | Next's **default image loader** with a small fixed set of widths (`images.deviceSizes` 480, 768, 1080, 1440, 1920; `imageSizes` 96, 160, 320, 640; one quality, 75; WebP only; 31-day optimizer cache), not a custom Cloudinary loader | Every upload is already resized to at most 2000 px and compressed to WebP on the server, so the stored original is small. With the default loader Cloudinary only serves that stored file (no transformation credits at all) and our server makes the resized copies once and caches them. A custom loader adding `f_auto,q_auto,w_<n>` would create up to one Cloudinary transformation per image per width (about eight per image) and spend free-plan credits for a saving we do not need. Widths outside the lists are never requested; the presets in `config/images.js` (thumb 160, card 640, hero 1920, banner 1440, avatar 96) only use listed widths and a test enforces it. Revisit if the shop grows past the free plan or if the host charges for image optimization. |
| Storage settings are checked on first use | `lib/storage/storage-env.js` | The three `CLOUDINARY_*` variables are required when `STORAGE_PROVIDER=cloudinary`, but they are validated when an upload, delete or the check script first runs, with a message naming the missing variable (never a value). Failing at import would break `next build`, tests and every page for a setting only the admin screens need. |
| Pictures of services, barbers and packages | An optional `image` object on the record: `{ mediaId, secureUrl, width, height, alt }` (D1, 2026-10-30) | The picture is uploaded first as a pending Media record (`/api/admin/catalog-image`), and only attached when the form saves, after the record itself saved. The record keeps a copy of the address and size for fast public reads (no join), and the Media record keeps the Cloudinary public id for deletes. Replacing or removing deletes the old Cloudinary file after the new state is saved; a failed delete flags the media `orphaned` and a sweep removes it later. Without a picture the site shows the slot image or placeholder, as before. Fixed shapes (presets): service-card 4:3, barber-portrait 4:5, package-card 4:3; the browser crops to them before upload, and all widths stay inside the fixed optimizer list. |
| Admin permissions are Super Admin controlled capabilities | A catalog of `<group>.<action>` capabilities in code, grants stored in MongoDB, enforced inside `requirePrincipal` and the dashboard guard (P1, 2026-10-30) | Existing static permissions stay as the ceiling; switches can only narrow an Admin, never widen. Defaults are all on so nothing changes until the Super Admin acts. Grants are read per call (no cache) so changes apply on the next click without re-login; the cost is one small read per guarded call. Fails closed for Admins. Replaces the open question about who may delete contact messages (it is now the switch `messages.delete`). Sign-in and TOTP were not touched. |

## D2a archive and restore (2026-10-31)
Owner decisions: only the Super Admin may permanently delete; an Admin cannot archive a barber with upcoming pending or confirmed bookings; restored records return hidden; D2a (services, packages, barbers) and D2b (gallery, messages, permanent delete) are separate; no automatic purge. Archived slugs stay reserved. Permanent delete is deferred to D2b because it needs its own confirmation screen and the stored-picture clean-up.

## Stage D availability (2026-10-31)
- One function computes every time's state; the page shows reasons instead of hiding times (earlier times today are collapsed into one note, since a wall of "Past" is noise).
- A conflict with an existing booking refuses the block and lists the bookings; it never offers to cancel them. Staff handle bookings with the normal booking actions.
- "Accepting bookings" (barber) and "bookable" (service) are separate from hidden and archived, and are read as true when missing, so existing data needs no migration.
- No separate "Complete early / Release / Reopen" buttons: cancel, complete and no-show already free the time. Block editing has a tested library function but no screen yet (unblock and create again).
