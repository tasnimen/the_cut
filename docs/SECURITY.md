# Security plan

**Status: Phase D is in progress and remains incomplete; public About/Gallery/Pricing/Contact preview routes add no mutation or private-data surface.** This is not a security certification. For this same-origin app, Better Auth's DB-backed session is selected and the separate access/refresh-token requirement is superseded; see [decisions](DECISIONS.md).

- Next.js Server Actions and Route Handlers are the selected server entry points for future business operations. Every entry point must authenticate, authorize, validate, apply ownership checks, and rate limit as appropriate. UI hiding is not authorization.
- Better Auth is the sole authentication/session authority, mounted at `/api/auth` with its MongoDB adapter and TOTP plugin. Use its revocable DB-backed session; do not create a parallel password/session system. See [AUTHENTICATION.md](AUTHENTICATION.md). Apply CSRF/origin protections and rate limits to every future mutation.
- Validate and normalize all request data at runtime; allowlist writable fields; bound payloads and pagination; safely handle errors without secrets or stack traces in public responses.
- Use HTTPS in production; add security headers; configure trusted proxy behavior deliberately; log security-relevant events without passwords, tokens, SMTP/API keys, or unnecessary PII. Current headers are listed below.
- Keep MongoDB, SMTP, and ImgBB credentials server-side. Never place secrets in `NEXT_PUBLIC_*`, source, logs, or docs. Zod validates optional server environment values; auth/db connections fail closed when their required values are missing.
- Protect sensitive operations with explicit role and resource ownership checks. Prevent public Super Admin creation; document and audit the initial bootstrap.
- Image upload: server-side authorization, file type/size constraints, provider response validation, safe replacement/deletion and orphan handling. ImgBB is for suitable public media only; no confidential documents or sensitive personal images. Terms, limits, deletion, and retention remain to be checked.
- Appointment creation/rescheduling rechecks availability during a concurrency-safe write. Protect against duplicate submissions and forged prices/durations.
- Define user data retention, deletion/export, review moderation, audit retention, incident response, dependency updates, and restore drills before launch.

## Implemented foundation

- `src/config/env.js` validates `NODE_ENV`, `SITE_URL`, MongoDB settings and Better Auth settings with Zod and is server-only. `.env.example` documents names only.
- `src/lib/db/mongo.js` owns a pooled server-only MongoDB client and creates unique user email/session token indexes, TTL indexes for Better Auth session/verification expiry, and query indexes for audit events including action/IP/time burst checks. On 2026-10-27, the local development auth handler returned HTTP 200 for `GET /api/auth/get-session`; `getAuth()` initializes the database and indexes before serving it. Signup, verification delivery, and production database configuration remain unverified.
- `src/lib/auth/server.js` configures Better Auth with MongoDB storage, email/password sign-in, role/status/sessionVersion fields that cannot be set by signup input, disabled cookie cache, secure production cookies, trusted origin, and TOTP. Failed email sign-in and TOTP verification results are append-audited without storing attempted email addresses; account identifiers are HMAC-pseudonymized. Five failures from one observed IP within ten minutes append a burst alert event. This is an in-app audit signal, not an external notification. Email verification is required but mail delivery is not configured until Phase F.
- Better Auth enforces origin/trusted-origin validation on its auth endpoint and uses its Mongo-backed rate limit store. General auth traffic is capped at 100/minute; sign-in is 5/minute, signup 5/hour, password reset 3/hour, reset completion 5/hour, verification mail 3/hour, and verification links 10/hour. These limits are shared through MongoDB. Trusted client-IP interpretation still depends on deployment proxy configuration.
- `src/app/api/auth/[...all]/route.js` is the Next.js Route Handler integration. `src/lib/auth/authorization.js` loads uncached database sessions, requires verified/active users, checks the role matrix, requires TOTP enrollment for Admin/Super Admin, and compares the session's stamped `sessionVersion` with the current user version. It exposes `requireRecentStepUp(principal)` for sensitive server operations. A verified TOTP request issues a ten-minute HttpOnly, SameSite=Strict proof cookie bound to that user and database session; the helper rejects expired, altered, or cross-session proofs. No privileged mutation route currently consumes the helper. A Better Auth user-update hook pre-increments `sessionVersion` when `role`, `status`, or `twoFactorEnabled` changes, so existing sessions are invalidated even if the subsequent field update fails. Unit tests cover bump criteria; DB-backed integration coverage remains outstanding. Direct DB writes must follow the same rule.
- `src/lib/security/audit-log.js` accepts strict bounded event fields and only appends records; privileged session creation, guard denials, failed sign-in/TOTP attempts, and failed-auth burst audit alerts are logged. Role/status changes and sensitive business actions do not yet have event producers.
- `src/lib/auth/policy.test.js` covers permission allow/deny defaults, session-version mismatch, and security-field version bump criteria; `security-events.test.js` covers failed-auth filtering, pseudonymization, and session-bound step-up token validation. This is not the full Section 11.1 attack-surface suite.
- `next.config.mjs` removes `X-Powered-By` and sets `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`, `Permissions-Policy`, and `Cross-Origin-Opener-Policy`; production responses receive HSTS.
- `src/proxy.js` generates a unique CSP nonce per request, sets request/response CSP, blocks scripts without a nonce, limits image/connect hosts, and sets `frame-ancestors 'none'`. Static assets bypass Proxy. All pages render dynamically; cache components and partial prerendering were disabled because installed Next.js docs say PPR is incompatible with nonce CSP. This increases server rendering cost and removes static/ISR caching.
- Better Auth production session-cookie configuration uses `__Host-better-auth.session_token`, `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`, and no Domain. Unit tests verify the generated cookie policy; a live sign-in `Set-Cookie` response remains unverified because no test account/email delivery flow is configured.
- Playwright/Edge against the production build returned 200 for `/`, `/services`, and `/booking` at 1440, 768 and 375px, with nonce CSP, nonce-bearing inline scripts, no console errors, and no horizontal overflow. The Next development overlay injects unnonced style elements, so development alone allows inline style elements; production keeps nonce-only style elements.
- No authentication route gate is active because there are no private UI routes yet. Proxy currently adds CSP only; real authorization is required inside every Server Action/Route Handler/DAL method.
- No Atlas-backed auth test, external failed-login notification, password-reset/verification mail, or session-version invalidation integration test has been completed. Recent TOTP step-up proof issuance and verification are implemented, but no sensitive action consumes the guard yet. These remain open work, not passed controls.
- `npm.cmd audit --omit=dev --offline` reported 0 vulnerabilities for installed production dependencies after Phase D package changes. Re-run online against current advisory data before release.

## Phase D security gate result

- **Partial / not DONE:** permission, session-version bump, cookie-policy, auth event, HMAC pseudonymization, and step-up token tests pass; auth endpoint rate limits/origin checks, `__Host-` cookie configuration, nonce CSP, failure/burst audit events, TOTP account lockout, and version bumps for role/status/2FA changes are configured. The local Mongo-backed auth handler smoke check returned HTTP 200. External failed-auth notifications, comprehensive auth attack tests, trusted-proxy/origin verification, live sign-in `Set-Cookie` response, email delivery, DB-backed session invalidation, sensitive-action step-up integration, and production database verification remain open. No business API can launch until applicable findings are closed.

## Phase E public-route checklist result

- About, Gallery, Pricing, and Contact preview paths are registered with `public` access in `src/config/routes.js` and linked through the shared desktop/mobile navigation. They read no private data and expose no Server Action, Route Handler mutation, upload, or external API call. Contact is explicitly informational; it does not accept or send messages.
- Gallery category filtering and image viewing are browser-only, use a small fixed local asset list, and expose no user-controlled query or persistence path. Concept imagery and incomplete business information are disclosed.
- `robots.txt` disallows `/api/` and the development-only design-system route. `sitemap.xml` includes only implemented public routes and omits URLs when `SITE_URL` is missing or local; production origin behavior still needs deployment validation.
- **Phase E checklist: no new authorization or data-mutation surface was introduced. Overall security remains PARTIAL** because Phase D's open controls above remain; this is not a launch/security certification.

## Phase C security checklist result (historical)

- The new `/design-system` route is marked `development-only` in `src/config/routes.js` and calls `notFound()` unless `NODE_ENV` is `development`; it returned 200 on the development server and 404 in the production HTTP smoke check. It is not included in navigation and contains no private data or privileged operations.
- Motion and R3F modules are client-only/deferred visual code. The 3D canvas is decorative (`aria-hidden`), dynamically imported with SSR disabled, and skipped for reduced-motion or low-power devices. It does not read or transmit user data.
- No authentication, database, mutation, upload, protected route, or authorization enforcement was added. Permission configuration remains descriptive. Existing CSP limitation remains open.
- Result: **no new authorization surface; foundation checklist partial**. This is not a penetration test or launch certification.
