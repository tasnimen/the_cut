# Security plan

**Status: Phases D and F are DONE-LOCAL with carryovers; Phase G is DONE-LOCAL but not live-ready.** This is not a security certification. For this same-origin app, Better Auth's DB-backed session is selected and the separate access/refresh-token requirement is superseded; see [decisions](DECISIONS.md).

## Email verification flag (2026-10-29)

`AUTH_REQUIRE_EMAIL_VERIFICATION` (default `false`) controls Better Auth `requireEmailVerification`, verification-mail sending, and the `emailVerified` check in `src/lib/auth/authorization.js` (`verification-policy.js`). With it off, an account can be created with an address the registrant does not own; all other protections stay. Turn it on before launch if that risk is unacceptable.

## Auth verification unit (2026-10-29)

- Verified live (dev app, DB `the_cut`, dummy account): sign-up without verification creates no verification token/record or mail; unverified sign-in works; wrong password and unknown email return the identical generic message and each write an `auth.sign_in.failed` audit entry; a guest booking attempt writes `authorization.denied`; sign-out clears the session (`get-session` null, protected API 401); Back shows the signed-out header.
- **Fixed:** Better Auth users have an ObjectId `_id` and no `id` field; lookups by `{ id }` in booking (create, no-show, confirmation/reminder email), session creation (sessionVersion stamp, admin session audit) and `session-version.js` never matched real users. All now use `userIdFilter` (`src/lib/db/user-filter.js`). Without it, booking creation returned `account_unavailable` and security-field updates (role/status/2FA, password-change version bump) were refused.
- `callbackUrl` is validated by `safeCallbackPath` (same-origin absolute paths only; no `//`, backslash, control characters, auth pages or `/api/`).
- Not present: password reset (no `sendResetPassword` configured, no UI); password-based per-account lockout (only IP rate limits, the failed-auth burst alert and TOTP lockout exist). Auth uses database sessions with one cookie; there is no separate refresh token.
- Live 429 was simulated by stubbing the response (a real 429 needs five failed sign-ins and triggers the owner alert email).

## Password reset (2026-10-29)

- Flow: `/forgot-password` posts to Better Auth `/request-password-reset` (per-IP limit 3/hour, existing custom rule); the response is identical for known and unknown addresses (tested); mail is sent in the background through Nodemailer and only to the account address; link host must equal the configured auth origin; token expires in one hour and is single-use (tested replay). `/reset-password` posts to `/reset-password` (limit 5/hour).
- On reset: all sessions are revoked (`revokeSessionsOnPasswordReset`), `sessionVersion` is bumped, and `auth.password_reset.completed` is audited; delivery failures are audited as `auth.password_reset.delivery_failed`.
- The reset page is `noindex` with `referrer: no-referrer` so the token in the URL is not leaked.
- Not tested live against a real mailbox (a real send would use the production SMTP provider).

## Avatar and deletion request (I-10, 2026-10-29)

`/api/account/avatar` (POST, DELETE): content-length required and capped, `requirePrincipal("mediaAvatarOwn")`, per-user rate limit (10 per hour), only the `file` field is read (no owner id, alt text or target from the client; alt text is generated server-side). The shared pipeline sniffs the real image type, rejects mismatches, limits pixels and re-encodes to WebP. Order: upload new, set `user.image`, delete older avatars of the same owner; if setting the image fails the new upload is removed. Delete only touches records with `category: "avatar"` and `ownerId` equal to the caller. The page renders a photo only when its URL is https on `i.ibb.co`. Unexpected errors are logged by name and message only and the client gets a generic message. Deletion request: Server Actions with `profileOwn`, per-user limit (5 per hour), the typed confirmation must equal the session's email (never taken from the client), one record per user, audited (`account.deletion.requested`, `account.deletion.cancelled`); nothing is deleted automatically. Tests: `avatar-core.test.js`, `deletion-actions.test.js`. **Note:** ImgBB URLs are public to anyone who has the link, so do not describe the photo as private.

## Profile, password and sessions (I-9, 2026-10-29)

Server Actions in `app/user/profile/actions.js`: each call runs `requirePrincipal` (`profileOwn` or `sessionsOwn`), a per-user rate limit (name 10/min, password 5/min, sessions 20/min), strict Zod parsing of known fields only (`lib/account/account-input.js`), then Better Auth's own API (`updateUser`, `changePassword`, `revokeSession`, `revokeOtherSessions`), then an audit event (`account.profile.updated`, `account.password.changed`, `account.password.change_failed`, `account.session.revoked`, `account.sessions.revoked_others`). Passwords are never logged, audited or returned. Only the display name is editable; the email is the sign-in identity and is read-only (changing it needs verification, deliberately not built). Changing the password revokes every session; the existing hook also bumps `sessionVersion`, so the current session ends too and the page clears its cookie and returns to sign-in. Session list: tokens never reach the browser; revoke takes a session id and the server resolves the token from the caller's own session list, so another user's id is "not found"; the current session cannot be revoked there (use Sign out); sessions from before the last password change are hidden. Tests: `account-input.test.js`, `app/user/profile/actions.test.js`.

## Customer appointments (I-8, 2026-10-29)

Ownership is enforced three times: the page loads bookings through `listMine({ principal })` (query `userId: principal.id`); the actions take the principal from `requirePrincipal("bookingOwn")`, never from the client; the repository's `cancel` and `reschedule` look the booking up with `{ _id, userId: principal.id }`, so another user's booking id returns "not found" (IDOR-safe). The cutoff and status rules live in the repository; the screens only mirror them (`bookingChangeOptions`). Errors shown to the customer are mapped to friendly text (`bookingErrorMessage`), never raw codes. Cancellation and reschedule emails use the shared `notifyBookingChange` (also used by the API routes); a failed email is audited and never blocks the change. Tests: `user-bookings.test.js` (split, 24-hour boundary, friendly messages), `app/user/actions.test.js` (permission on every call, principal passed to the repository, bad ids/times rejected, friendly errors, no email on failure). Live check on a production build with a dummy customer: booked, rescheduled (Wed to Tue) and cancelled through the dashboard.

## Business settings editor (I-7, 2026-10-29)

Same write pattern with the existing permission `businessSettingsManage` (ADMIN and SUPER_ADMIN) and rate bucket `admin-settings` (20 per minute per admin); four separate Server Actions (hours, closed dates, contact, social) so each save changes one document. Validation: hours on the 15-minute grid, at least an hour long, at least one open day; closed dates real calendar dates (max 120); phone 7 to 15 digits with only phone characters; email checked; address at most 120 characters, postal code pattern; social links must be https, without credentials, and on the network's own domain (blocks `javascript:`, look-alike hosts such as `instagram.com.evil.example` and other networks). Unknown form keys are ignored. The audit log stores only which fields are set or how many days or dates changed, never phone numbers, emails, addresses or URLs. Tests: `settings`, `settings-input`, `admin-settings`, `actions.test.js` (denied writes nothing on all four actions, rate limit, mass assignment, bad input writes nothing). **Not run live with an Admin session.**

## Barbers editor (I-17, 2026-10-29)

Same write pattern as I-15/I-16 with permission `barbersManageAll` (ADMIN and SUPER_ADMIN, already in the matrix) and rate bucket `admin-barbers` (30 per minute per admin). Specifics: the schedule written is exactly what the booking engine reads (`weeklySchedule`, one `breaks` entry per day, `daysOff` dates); times must sit on the 15-minute grid, a working day is at least one hour long, a break must be at least 15 minutes and inside working hours, days off must be real calendar dates (max 400), services must exist (rejected, not dropped), an active barber needs at least one service and one working day; unknown form keys are ignored and the slug cannot change on edit. The schedule is replaced wholesale so removing a day really removes it. No hard delete: barbers are switched off, which removes them from availability while keeping booking history. Changing hours does not move existing appointments (the screens say so). The public-profile fields (`publicProfile`, `role`, `focus`, `displayOrder`) feed the home team section only for barbers marked public. Audit: `catalog.barber.created|updated|activated|deactivated` (updates list what changed: services count, schedule, breaks, days-off count, profile flags). Tests: `barber-input` (includes a run through the real slot generator showing the lunch break removes its slot), `admin-barbers`, `actions.test.js` (denied writes nothing on all three actions, rate limit, unknown services and off-grid times rejected, typed values returned, slug ignored on edit). **Not run live with an Admin session.**

## Admin write pattern and the services editor (I-15, 2026-10-29)

Pattern every admin write follows (reuse it in later units): the page calls `requireDashboardAccess("admin")`; each Server Action calls `requirePrincipal(<permission>)` itself (session, status, role, session version, TOTP enrolment, denial audit), then a per-admin rate limit (`consumeUserRateLimit`, 30 per minute for services), then strict Zod parsing of **only the known form keys** (unknown keys are ignored; the schemas are `.strict()`), then the repository write, an audit event, and `revalidateCatalog()`. Errors shown to the user are generic.

- Services editor (`/admin/services`, `/new`, `/[slug]`): permission `servicesManageAll` (ADMIN and SUPER_ADMIN). Price is entered in dollars and converted to integer cents (max $9,999.99, must be positive); duration 5 to 480 minutes; slug (create only) lowercase letters, numbers, hyphens, unique (the database unique index also enforces it); the slug and the `currency` field can never be changed by an edit. No hard delete: services are hidden instead, so booking history and barber assignments stay intact.
- Audit: `catalog.service.created`, `.updated` (with changed fields, e.g. `priceMinorUnits: 2500->3000`; names and descriptions only as "changed"), `.activated`, `.deactivated`. `appendAuditEvent` now accepts an optional `details` map of short strings (max 12 keys).
- Tests: `service-input.test.js` (price parsing, mass assignment, slug rules), `admin-services.test.js` (create, duplicate, update, not found, hide/show, audit), `actions.test.js` (permission checked on every call, denied writes nothing, rate limit stops before the database, slug argument validated, form keys ignored). **Not run live:** the editor with a real Admin session (the assistant has no admin credentials); manual steps are in `docs/TESTING.md`.

## Two-step verification for admins (I-3, 2026-10-29)

- Enrolment page `/two-factor` (guard `requireEnrolmentAccess`, pure rule `decideEnrolmentAccess`): guests go to sign-in and return; customers and suspended accounts get 404; already-enrolled admins go to their dashboard; page is `noindex`, `no-store`, disallowed in `robots.txt`.
- Flow (Better Auth `twoFactor` plugin): confirm the password (`/two-factor/enable`), receive the setup key and one-time backup codes (shown once, kept only in component state), then prove the authenticator with a first code (`/two-factor/verify-totp`); two-factor is switched on by the server only after that code. Enabling changes `twoFactorEnabled`, which bumps `sessionVersion` and invalidates the session, so the admin signs in again and meets the challenge.
- Sign-in challenge: when the response is `twoFactorRedirect`, the sign-in page shows a code step (authenticator code or a single-use backup code). No session exists until it succeeds; a successful TOTP also issues the existing step-up proof cookie. Failures use one generic message; 429 and 5xx map to their own toasts.
- Limits: `/two-factor/*` is rate limited (10 per minute per IP) on top of the plugin's account lockout (5 failed attempts, 15 minutes) and the existing failed-auth audit and burst alert.
- Tests: `two-factor-flow.test.js` (in-memory Better Auth: enrol, code needed before 2FA turns on, challenge at sign-in, wrong code refused, backup code single use, wrong password refused), `two-factor.test.js`, `dashboard-access.test.js`. **Not run live:** the enrolment pages with a real Admin (none seeded yet).

## Seeded admin accounts (2026-10-29)

`npm run seed:admins:dev` (`scripts/seed-admins.js`, pure logic in `src/lib/auth/admin-seed-core.js`) creates the first SUPER_ADMIN and an optional test ADMIN from `SEED_SUPER_ADMIN_*` / `SEED_ADMIN_*`. Each creation or promotion writes a `seed.account.*` audit event.

## Phase G booking controls (updated 2026-10-29)

- Better Auth is mandatory for booking ownership reads and mutations; authorization checks verified email, ACTIVE status, session version, role, and admin TOTP. Customer operations scope Mongo queries to the session user. No-show is restricted to `bookingsManageAll`.
- Strict Zod schemas reject unknown payload fields. Public availability and each mutation have Mongo-backed per-IP limits. User-supplied price/duration is never accepted; the server reads service records and snapshots their values. The approved catalog exists in source; until database service rows are reconciled and seeded, price validation blocks confirmation. The database was not inspected or modified.
- Create/cancel/reschedule/no-show and occupancy rows share Mongo transactions. The unique `{barberId, slotStart}` index claims each quarter-hour including cleanup buffer to prevent overlaps/races. Requires a transaction-capable Mongo deployment.
- Booking APIs return DTOs; internal/provider errors are not included. Email is deferred with `after()`; failures write generic audit actions without provider details. No SMTP values are in client code.
- Seed script defaults to a read-only preflight and requires `NODE_ENV=development` plus a resolved database name exactly `the_cut`. Writes additionally require `--apply` and `ALLOW_THE_CUT_BOOKING_SEED=YES_I_REVIEWED_THE_CUT_DATABASE`; the script was not run. No production limits or environment secrets were read or changed.
- **Checklist:** PASS: owner/admin authorization; server-authoritative service values; strict input validation; rate limiting; transaction/unique slot reservation; redacted mail failures; unset/invalid prices fail closed. NOT VERIFIED: actual `the_cut` data/preflight, Atlas transactions and real role sessions, barber schedules, live email, or browser booking.

- Next.js Server Actions and Route Handlers are the selected server entry points for future business operations. Every entry point must authenticate, authorize, validate, apply ownership checks, and rate limit as appropriate. UI hiding is not authorization.
- Better Auth is the sole authentication/session authority, mounted at `/api/auth` with its MongoDB adapter and TOTP plugin. Use its revocable DB-backed session; do not create a parallel password/session system. See [AUTHENTICATION.md](AUTHENTICATION.md). Apply CSRF/origin protections and rate limits to every future mutation.
- Validate and normalize all request data at runtime; allowlist writable fields; bound payloads and pagination; safely handle errors without secrets or stack traces in public responses.
- Use HTTPS in production; add security headers; configure trusted proxy behavior deliberately; log security-relevant events without passwords, tokens, SMTP/API keys, or unnecessary PII. Current headers are listed below.
- Keep MongoDB, SMTP, and ImgBB credentials server-side. Never place secrets in `NEXT_PUBLIC_*`, source, logs, or docs. Zod validates optional server environment values; auth/db connections fail closed when their required values are missing.
- Protect sensitive operations with explicit role and resource ownership checks. Prevent public Super Admin creation; document and audit the initial bootstrap.
- Image upload: server-side authorization, file type/size constraints, provider response validation, safe replacement/deletion and orphan handling. ImgBB is for suitable public media only; no confidential documents or sensitive personal images. Terms, limits, deletion, and retention remain to be checked.
- Appointment creation/rescheduling rechecks availability during a concurrency-safe write. Protect against duplicate submissions and forged prices/durations.
- Define user data retention, deletion/export, review moderation, audit retention, incident response, dependency updates, and restore drills before launch.

## Implemented foundation

- `src/config/env.js` validates `NODE_ENV`, `SITE_URL`, MongoDB settings and Better Auth settings with Zod and is server-only. `.env.example` documents names only.
- `src/lib/db/mongo.js` owns a pooled server-only MongoDB client and creates unique user email/session token indexes, TTL indexes for Better Auth sessions, verification records, and hashed one-time email-verification tokens, plus query indexes for audit events including action/IP/time burst checks. On 2026-10-27, the local development auth handler returned HTTP 200 for `GET /api/auth/get-session`; `getAuth()` initializes the database and indexes before serving it. Signup and production database configuration remain unverified.
- `src/lib/auth/server.js` configures Better Auth with MongoDB storage, email/password sign-in, role/status/sessionVersion fields that cannot be set by signup input, disabled cookie cache, secure production cookies, trusted origin, and TOTP. Failed email sign-in and TOTP verification results are append-audited without storing attempted email addresses; account identifiers are HMAC-pseudonymized. Five failures from one observed IP within ten minutes append a burst alert event and queue an email to `MAIL_TO`.
- Better Auth enforces origin/trusted-origin validation on its auth endpoint and uses its Mongo-backed rate limit store. General auth traffic is capped at 100/minute; sign-in is 5/minute, signup 5/hour, password reset 3/hour, reset completion 5/hour, verification mail 3/hour, and verification links 10/hour. These limits are shared through MongoDB. Trusted client-IP interpretation still depends on deployment proxy configuration.
- `src/lib/mail/mailer.js` reads SMTP settings only through server-only `src/config/env.js` and sends through Nodemailer. Verification tokens expire after one hour; token hashes are stored in `emailVerificationToken` and atomically consumed by `src/app/api/auth/[...all]/route.js`, so unknown, expired, and replayed links are rejected. Sign-up and unverified sign-in schedule mail with Next.js `after()`. Five failed sign-in/TOTP events from one source IP within ten minutes trigger a security email to `MAIL_TO`. Delivery failures are audit-logged as generic events without SMTP error text or attempted email addresses. All six SMTP variable names were present; a live transport check authenticated and its provider accepted one smoke message. No values were inspected; inbox receipt and auth-flow delivery remain unverified.
- `src/app/api/auth/[...all]/route.js` is the Next.js Route Handler integration. `src/lib/auth/authorization.js` loads uncached database sessions, requires verified/active users, checks the role matrix, requires TOTP enrollment for Admin/Super Admin, and compares the session's stamped `sessionVersion` with the current user version. It exposes `requireRecentStepUp(principal)` for sensitive server operations. A verified TOTP request issues a ten-minute HttpOnly, SameSite=Strict proof cookie bound to that user and database session; the helper rejects expired, altered, or cross-session proofs. No privileged mutation route currently consumes the helper. A Better Auth user-update hook pre-increments `sessionVersion` when `role`, `status`, or `twoFactorEnabled` changes, so existing sessions are invalidated even if the subsequent field update fails. Unit tests cover bump criteria; DB-backed integration coverage remains outstanding. Direct DB writes must follow the same rule.
- `src/lib/security/audit-log.js` accepts strict bounded event fields and only appends records; privileged session creation, guard denials, failed sign-in/TOTP attempts, and failed-auth burst audit alerts are logged. Role/status changes and sensitive business actions do not yet have event producers.
- `src/lib/auth/policy.test.js` covers permission allow/deny defaults, session-version mismatch, and security-field version bump criteria; `security-events.test.js` covers failed-auth filtering, pseudonymization, and session-bound step-up token validation. This is not the full Section 11.1 attack-surface suite.
- Successful Better Auth `/change-password` requests now increment the user's `sessionVersion`; `policy.test.js` verifies an older stamped session is rejected after that bump. This is a unit test with a fake collection, not an Atlas-backed session integration test.
- JWT tampering/expiry/`alg:none` and refresh-token family reuse remain **not applicable to the selected Better Auth opaque-session design** and are not represented as passing tests. Logout invalidation still needs a direct test against Better Auth's DB session behavior. No separate test database was contacted for this local unit-test work.
- `src/lib/auth/request-security.js` centralizes the Better Auth Mongo-backed rate-limit policy, rejects structured/unknown sign-in fields before dispatch, constrains primitive filter values to allow-listed keys, and normalizes 401 sign-in text with a 500 ms minimum response floor. `request-security.test.js` covers `$ne` payload/filter rejection, active rate-limit caps, same-message failures, and delay-floor calculation. There are no server-side business filter routes yet; the filter test covers the shared guard contract, not a live database query.
- Better Auth sign-in/sign-up JSON responses pass through `stripSessionTokenFromResponse`, so opaque session tokens are not exposed to page JavaScript; the HttpOnly session cookie is preserved. Auth UI forms call the same-origin Route Handler and never persist credentials or tokens. The public auth pages read only the current session to redirect authenticated users and contain no private account data.
- `session-lifecycle.test.js` exercises signup, wrong-password rejection, correct sign-in, sign-out, then stale-cookie session lookup through Better Auth's in-memory adapter. It confirms library logout invalidates the session without touching Atlas; the production Mongo adapter path remains unverified.
- `policy.test.js` generates role checks for every permission entry in `src/config/permissions.js`; this verifies the configured authorization matrix. No dashboard routes exist yet, so no private route handler can be exercised against real role sessions.
- `next.config.mjs` removes `X-Powered-By` and sets `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`, `Permissions-Policy`, and `Cross-Origin-Opener-Policy`; production responses receive HSTS.
- `src/proxy.js` generates a unique CSP nonce per request, sets request/response CSP, blocks scripts without a nonce, limits image/connect hosts, and sets `frame-ancestors 'none'`. Static assets bypass Proxy. All pages render dynamically; cache components and partial prerendering were disabled because installed Next.js docs say PPR is incompatible with nonce CSP. This increases server rendering cost and removes static/ISR caching.
- Better Auth production session-cookie configuration uses `__Host-better-auth.session_token`, `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`, and no Domain. Unit tests verify the generated cookie policy; a live sign-in `Set-Cookie` response remains unverified because no test account was created and no email was sent.

The Next development overlay injects unnonced style elements, so development alone allows inline style elements; production keeps nonce-only style elements.
- No authentication route gate is active because there are no private UI routes yet. Proxy currently adds CSP only; real authorization is required inside every Server Action/Route Handler/DAL method.
- No Atlas-backed auth test, external failed-login notification, password-reset/verification mail, or session-version invalidation integration test has been completed. Recent TOTP step-up proof issuance and verification are implemented, but no sensitive action consumes the guard yet. These remain open work, not passed controls.
- `npm.cmd audit --omit=dev --offline` reported 0 vulnerabilities for installed production dependencies after Phase D package changes. Re-run online against current advisory data before release.

## Phase F media and contact checklist

- `/api/media` authenticates and checks category-specific permissions. ADMIN/SUPER_ADMIN can upload/delete gallery, product, barber, and service media; verified USER/ADMIN/SUPER_ADMIN accounts can manage only their own avatar. Uploads are capped at 5 MiB, allow JPEG/PNG/WebP/AVIF by magic bytes and matching declared MIME, reject animated/malformed content, resize to at most 2000px, convert to WebP with Sharp (which strips metadata on output), and use random filenames. Mongo stores media metadata and the ImgBB `deleteUrl`; API responses omit `deleteUrl`.
- `IMGBB_API_KEY` is read only in server-only storage modules. The key is sent only to the ImgBB server; image responses are constrained to HTTPS `i.ibb.co`, delete URLs to HTTPS `ibb.co`, with redirects disabled. Upload/delete operations have hashed per-IP rate limits and bounded retry behavior. `next/image` is allow-listed to `i.ibb.co`; shared images fall back to a local placeholder. - Contact messages are strict-Zod validated, capped by field length, email-header CRLF is rejected, and user content is HTML escaped.
