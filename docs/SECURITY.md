# Security plan

**Status: Phases D and F are DONE-LOCAL with carryovers; Phase G is DONE-LOCAL but not live-ready.** This is not a security certification. For this same-origin app, Better Auth's DB-backed session is selected and the separate access/refresh-token requirement is superseded; see [decisions](DECISIONS.md).

## Email verification flag (2026-10-29)

`AUTH_REQUIRE_EMAIL_VERIFICATION` (default `false`) controls Better Auth `requireEmailVerification`, verification-mail sending, and the `emailVerified` check in `src/lib/auth/authorization.js` (`verification-policy.js`). With it off, an account can be created with an address the registrant does not own; all other protections stay. Turn it on before launch if that risk is unacceptable.

## Auth verification unit (2026-10-29)

- Verified live (dev app, DB `the_cut`, dummy account): sign-up without verification creates no verification token/record or mail; unverified sign-in works; wrong password and unknown email return the identical generic message and each write an `auth.sign_in.failed` audit entry; a guest booking attempt writes `authorization.denied`; sign-out clears the session (`get-session` null, protected API 401); Back shows the signed-out header.
- **Fixed:** Better Auth users have an ObjectId `_id` and no `id` field; lookups by `{ id }` in booking (create, no-show, confirmation/reminder email), session creation (sessionVersion stamp, admin session audit) and `session-version.js` never matched real users. All now use `userIdFilter` (`src/lib/db/user-filter.js`). Without it, booking creation returned `account_unavailable` and security-field updates (role/status/2FA, password-change version bump) were refused.
- `callbackUrl` is validated by `safeCallbackPath` (same-origin absolute paths only; no `//`, backslash, control characters, auth pages or `/api/`).
- Not present: password reset (no `sendResetPassword` configured, no UI); password-based per-account lockout (only IP rate limits, the failed-auth burst alert and TOTP lockout exist). Auth uses database sessions with one cookie; there is no separate refresh token.
- Live 429 was simulated by stubbing the response (a real 429 needs five failed sign-ins and triggers the owner alert email).

## Password reset (2026-10-29)

- Flow: `/forgot-password` posts to Better Auth `/request-password-reset` (per-IP limit 3/hour, existing custom rule); the response is identical for known and unknown addresses (tested); mail is sent in the background through Nodemailer and only to the account address; link host must equal the configured auth origin; token expires in one hour and is single-use (tested replay). `/reset-password` posts to `/reset-password` (limit 5/hour).
- On reset: all sessions are revoked (`revokeSessionsOnPasswordReset`), `sessionVersion` is bumped, and `auth.password_reset.completed` is audited; delivery failures are audited as `auth.password_reset.delivery_failed`.
- The reset page is `noindex` with `referrer: no-referrer` so the token in the URL is not leaked.
- Not tested live against a real mailbox (a real send would use the production SMTP provider).

## Admin permission screen (P2, 2026-10-30)

`saveAdminPermissionsAction` runs in this order and stops at the first failure: session, TOTP and `securitySettingsManage` (Super Admin only; an Admin is refused), per-user rate limit (20 per minute), recent authenticator code (`requireRecentStepUp`, 10 minutes; without it the action refuses and the screen asks for the code), strict validation (`validateGrantsInput`: known capability ids with booleans, nothing else), then the save (audited with counts only). A test checks this order in the source. The screen cannot grant what is not in the catalog, so Super Admin areas (this page, audit, accounts, security settings, revenue) can never be handed to an Admin. Hidden menu entries and buttons are convenience only; the server enforcement from P1 is unchanged and independent of what the interface shows.

## Super Admin controlled Admin capabilities (P1, 2026-10-30)

Every Admin page, Server Action and admin API route now also asks `roleHasCapability(role, capability)` (`lib/auth/capabilities.js`) after the existing session, status, role, TOTP and permission checks, through `requirePrincipal(permission, { capability })` and `requireDashboardAccess("admin", { capability })`. The check reads one small MongoDB document on every call (no cache), so a revoke applies on the next click. Only ADMIN is checked; SUPER_ADMIN is never limited; anything unknown, any read failure, and any role other than ADMIN or SUPER_ADMIN is a refusal (fail closed). A revoked page is a 404, a revoked action returns the usual "not allowed", and the denial is audited (`authorization.denied`). The stored grants are validated on resolve (unknown keys and non-booleans are ignored, so a tampered document cannot add power) and on save (`validateGrantsInput`: known ids with booleans only). Sign-in, TOTP, session version and role detection are untouched (tested: an Admin without TOTP or a suspended Admin is still refused). `capability-coverage.test.js` fails if a new admin entry point forgets its capability, passes an unknown one, or a page uses the wrong route key. Details: [ADMIN_PERMISSIONS.md](ADMIN_PERMISSIONS.md).

## Pictures for services, barbers and packages (D1, 2026-10-30)

Upload: `POST /api/admin/catalog-image` reads only `kind` (services, barbers or packages) and `file`; the permission of that kind is required on every call, then a per-user limit (40 per hour), the 4 MB cap and the shared pipeline (type sniffing, EXIF stripping, WebP). Nothing is attached at upload time. `DELETE` (strict JSON, `kind` and `mediaId` only) discards a pending upload and refuses anything already attached (409). Attaching happens in the save actions, after the record saved: the action checks the picture permission again, the media must exist, be of the same kind and be unattached or already this record's (`attachedTo`), so one record cannot take another record's asset; the form can send only `imageMediaId`, `imageAlt` and `removeImage` (never an address or size; the address comes from the Media record). The description is required with a picture (5 to 200 characters, no markup). Old pictures are deleted (Cloudinary file and Media record) after the new state is saved, with an audit entry (`catalog.image_attached|replaced|removed|alt_updated|delete_failed`); a failed delete flags the asset for a sweep, so no file is lost. Public pages only receive an allow-listed picture (`url`, `alt`, size) from a trusted host, never the media id. Tests: `image-input`, `catalog-images`, `image-action`, the three action tests and the route test.

## Operational reports (I-22, 2026-10-30)

Read-only page: `requireDashboardAccess("admin")` then `requirePrincipal("operationalReportsAll")`. The only input is `?range=`, accepted from a fixed list (last 7, 30 or 90 days, next 7 days; anything else, including objects, becomes the default), so there is no free-form query or date from the browser. One MongoDB aggregation over bookings of the range (a single `$facet`, groups capped at 30 barbers and 10 services) plus one count of new customer accounts. The output holds counts, rates and labels (barber and service names, weekday, hour) only: no prices, no customer names, emails or phones, no ids (tested). Weekday and hour use the shop's time zone, and range bounds are whole business days across the daylight-saving change (tested). Tests: `lib/reports/operational.test.js`.

## Image uploads in the browser and image delivery (C2, 2026-10-30)

Browser: before sending, photos are shrunk to 2000 px and re-encoded to WebP (`lib/images/client-upload.js`; the canvas also drops EXIF) so they stay under 4 MB; this is a convenience only, and the server repeats every check (type sniffing, size, re-encode). Errors show one clear toast each: too large, wrong type, rate limited, signed out, image service unavailable, network. Failed remote images show the placeholder instead of a broken icon (`ImageWithFallback`), with a blur placeholder and a fixed aspect ratio. Delivery guard (`image-delivery.test.js`): the optimizer config matches the fixed width lists, no `unoptimized`, custom loader or off-list quality, every `fill` image has a `sizes` hint, no plain `<img>`. Slot overrides: `isTrustedImageUrl` guards each address, unknown slot keys are ignored, writes need `mediaSlotsManageAll` (helpers only; no screen yet) and are audited (`images.slot_set`, `images.slot_cleared`). Tests: `client-upload.test.js`, `image-delivery.test.js`, `slot-overrides.test.js`.

## Image storage on Cloudinary (C1, 2026-10-30)

All image traffic to Cloudinary is server-to-server: uploads (`image/upload`) and deletes (`image/destroy`) are signed with SHA-1 over the sorted parameters plus `CLOUDINARY_API_SECRET`; the secret, the signature and the API key are never logged, returned, put in an error, or sent to a browser (`cloudinary.js` returns codes only; tests assert the secret never appears in outputs; `no-secret-in-client.test.js` checks that no client component imports the adapter or the server env or names the variables; none of the variables is `NEXT_PUBLIC_`). Rules kept from before: login required, role check per target (a customer may only upload and delete their own avatar; admins for gallery, services, barbers, banners, slots, products; guests never), real type sniffing and spoofed-MIME rejection, 4 MB cap (checked on the declared length, the file size and again after re-encoding), re-encode to WebP at most 2000 px on the long side with EXIF and GPS removed (tested with a JPEG that carries both), per-user rate limits (uploads 10 per hour on `/api/media`, other routes as before; the generic route used to be per IP), generic messages to users (details only in the server log: error name and message, never values), and an audit event for every upload and delete (`media.uploaded`, `media.deleted`, with the category only). New: fixed folders per target (`the-cut/avatars|barbers|services|gallery|banners|slots|products`, `the-cut/_test` for the check script) and a random UUID public id, `overwrite=false`, so no part of a path comes from a user; deletes accept only ids matching `the-cut/<folder>/<uuid>` and use the stored public id, not a URL. A provider response is accepted only if the returned id equals the requested one and the address is https on `res.cloudinary.com/<cloud name>/`. Browsers may load images only from `self`, `res.cloudinary.com/<cloud name>/` (path-scoped in the CSP and in `images.remotePatterns`) and, for older images, `i.ibb.co`; `connect-src` no longer lists any image service because the browser never talks to one. `isTrustedImageUrl` guards every address before it is rendered. Legacy (ImgBB) Media records have no `provider` field, stay readable, and are deleted through the old adapter if `IMGBB_API_KEY` is set. Credential check: `npm run check:cloudinary` (development only, refuses to run when `NODE_ENV=production`, prints SUCCESS or FAILURE plus a safe code only). Tests: `cloudinary.test.js`, `upload-policy.test.js`, `image-processor.test.js`, `app/api/media/route.test.js`, `no-secret-in-client.test.js`, `images/trusted-url.test.js`.

## Gallery manager (I-19, 2026-10-30)

Upload: `POST /api/admin/gallery` (multipart). Order of checks: content-length present and under 5 MB plus form overhead, `requirePrincipal("mediaGalleryManageAll")`, per-user rate limit (30 per hour), file present and under 5 MB, strict Zod for `title`, `category` (fixed list) and `alt`, gallery size cap (200). The image then goes through the shared pipeline (real type sniffing, pixel limit, re-encode to WebP, ImgBB upload); the stored address, size and owner come from the pipeline, never from the request. If saving the gallery item fails the uploaded file is removed again. Edit, show/hide and delete are Server Actions with the same permission, a rate limit (60/min), a 24-hex id, and strict schemas (an image address or any extra key is rejected). Delete removes the provider file first and keeps the item if the provider fails (the admin is told, and can hide it instead), so nothing half-deleted remains. The provider's delete address is stored only in `media` and is never returned to browsers or the public site. The public page renders only active items whose address is https on `i.ibb.co`, with titles and descriptions as escaped text. Audit: `gallery.item_created|updated|shown|hidden|deleted` (category only, never titles). Unexpected upload errors are logged by name and message only. Reminder for the owner: only upload photos you have the right to use, with the permission of recognisable people. Tests: `gallery-input.test.js`, `admin-gallery.test.js`, `app/admin/gallery/actions.test.js`.

## Contact messages (I-20, 2026-10-30)

Read: the pages call `requireDashboardAccess("admin")` then `requirePrincipal("contactManageAll")`. The message body is customer-supplied text, so it is only ever rendered as React text (escaped, `white-space: pre-wrap`), never as HTML. The reply link is `mailto:` built from the stored address (validated by Zod at submit time, no line breaks) with a fixed encoded subject, so message content can never inject mail headers or a different link. Status changes (`contactManageAll`) and deletes (`contactDeleteAll`, Admin and Super Admin since the owner's decision on 2026-10-30) are Server Actions with their own permission check, a per-user rate limit (60/min), a strict id (24 hex) and a fixed status list. Audit events (`contact.status_changed`, `contact.deleted`) record who and which message, never the text or the email address. Listing is paged (25), search text is cleaned and regex-escaped, projection is explicit. Customers' email addresses and messages are personal data: pages are `noindex`. Tests: `admin-messages.test.js`, `app/admin/messages/actions.test.js` (including "delete only when the caller holds contactDeleteAll").

## Customers list (I-14, 2026-10-29)

Read-only page. Guard: `requireDashboardAccess("admin")`, then `requirePrincipal("customersRead")`. The query is always `{ role: "USER" }` plus optional filters, so admins and super admins never appear; the user projection lists exactly name, email, createdAt, status, noShowCount and adminReviewRequired (no password hash, no sessions, no accounts, no role), and `shapeCustomer` copies only the display fields. Search text is cleaned (non-string values dropped, control characters removed, 60 characters) and regex-escaped; page size 25, page capped at 1000. Booking statistics come from one aggregate limited to the ids on the page (`$match userId $in`), and pending deletion requests from one indexed lookup. Walk-in bookings have synthetic owners so they never count toward a customer. Tests: `customers.test.js` (parsing, query, limited fields, loader). Note: email addresses are personal data; the page is `noindex` and only admins can open it.

## Walk-in booking (I-13, 2026-10-29)

Two Server Actions (`app/admin/bookings/walk-in/actions.js`), each with `requirePrincipal("bookingsManageAll")` and a per-user rate limit (availability 60/min, create 20/min). Input is strict Zod (`lib/booking/walk-in.js`): name 2 to 100 characters without control characters or angle brackets, optional US phone, 1 to 3 unique service slugs, an ISO time, a barber slug; unknown keys (price, duration, userId) are rejected. Price, duration, end time and barber come from the database inside the booking transaction; the slot is re-checked and claimed with the same unique slot rows as online bookings, so a walk-in and an online booking can never take the same slot. The only rule relaxed for admins is the 60-minute lead time (a slot may start now; slots that already started are still excluded). The synthetic `walkin:` owner cannot match a real user. Walk-ins get no email, text or reminder, and cancelling one sends nothing. Audit: `booking.walk_in_created`. Availability replies contain slugs and names only, never ids. Tests: `walk-in.test.js`, walk-in cases in `repository.test.js`, `app/admin/bookings/walk-in/actions.test.js`.

## All bookings search (I-12, 2026-10-29)

Filters come from the URL, so `parseBookingFilters` accepts only known keys, takes the first value of repeats, strips control characters, caps the search at 60 characters and the page at 1000, allows only the five statuses, a 24-hex barber id and real calendar dates; anything else is dropped (objects smuggled in as values become empty). The search text is regex-escaped before it reaches MongoDB, so `.*` or `(` match literally; phone search uses digits only (3 or more); a 24-hex search also matches the booking id. Page size is fixed at 25 and the sort is stable. The data is only read after `requireDashboardAccess("admin")`; no user id is returned. Performance note: name and phone searches use unanchored regex and scan the `booking` collection (fine at shop scale; add a text index or a normalized search field if it grows into the tens of thousands). Tests: `admin-bookings.test.js` (parsing, query building, query strings) and the "admin booking search" cases in `repository.test.js` (paging, status/barber/date filters, name/phone/id search, special characters, no user ids).

## Admin bookings (I-11, 2026-10-29)

`app/admin/bookings/actions.js`: `requirePrincipal("bookingsManageAll")` on every call, per-user rate limit (60/min), booking id validated (24 hex), target must be one of confirmed, completed, cancelled, no_show. `repository.adminChangeStatus` runs in a transaction and re-checks what is allowed now (`adminAllowedActions`: completing needs the start time to have passed, no-show needs the late-arrival grace to have passed, finished bookings never change; the update also filters on the previous status so two admins cannot both win). Cancelling frees the slots and emails the **customer** (`notifyBookingChange` now takes `recipientUserId`; before, the acting user's address was always used). Audit actions: `booking.confirmed_by_admin`, `booking.completed`, `booking.cancelled_by_admin`, `booking.no_show`. The day list omits the customer's user id; it shows name and phone, which admins need to contact the customer. Tests: `admin-bookings.test.js`, `repository.test.js` (admin cases), `app/admin/bookings/actions.test.js`. Not done: the step-up (recent TOTP) requirement listed in `config/routes.js` for no-show is not enforced by the existing route either; decide in the hardening units (I-28 to I-30).

## Avatar and deletion request (I-10, 2026-10-29)

`/api/account/avatar` (POST, DELETE): content-length required and capped, `requirePrincipal("mediaAvatarOwn")`, per-user rate limit (10 per hour), only the `file` field is read (no owner id, alt text or target from the client; alt text is generated server-side). The shared pipeline sniffs the real image type, rejects mismatches, limits pixels and re-encodes to WebP. Order: upload new, set `user.image`, delete older avatars of the same owner; if setting the image fails the new upload is removed. Delete only touches records with `category: "avatar"` and `ownerId` equal to the caller. The page renders a photo only when its URL is https on `i.ibb.co`. Unexpected errors are logged by name and message only and the client gets a generic message. Deletion request: Server Actions with `profileOwn`, per-user limit (5 per hour), the typed confirmation must equal the session's email (never taken from the client), one record per user, audited (`account.deletion.requested`, `account.deletion.cancelled`); nothing is deleted automatically. Tests: `avatar-core.test.js`, `deletion-actions.test.js`. **Note:** ImgBB URLs are public to anyone who has the link, so do not describe the photo as private.

## Profile, password and sessions (I-9, 2026-10-29)

Server Actions in `app/user/profile/actions.js`: each call runs `requirePrincipal` (`profileOwn` or `sessionsOwn`), a per-user rate limit (name 10/min, password 5/min, sessions 20/min), strict Zod parsing of known fields only (`lib/account/account-input.js`), then Better Auth's own API (`updateUser`, `changePassword`, `revokeSession`, `revokeOtherSessions`), then an audit event (`account.profile.updated`, `account.password.changed`, `account.password.change_failed`, `account.session.revoked`, `account.sessions.revoked_others`). Passwords are never logged, audited or returned. Only the display name is editable; the email is the sign-in identity and is read-only (changing it needs verification, deliberately not built). Changing the password revokes every session; the existing hook also bumps `sessionVersion`, so the current session ends too and the page clears its cookie and returns to sign-in. Session list: tokens never reach the browser; revoke takes a session id and the server resolves the token from the caller's own session list, so another user's id is "not found"; the current session cannot be revoked there (use Sign out); sessions from before the last password change are hidden. Tests: `account-input.test.js`, `app/user/profile/actions.test.js`.

## Customer appointments (I-8, 2026-10-29)

Ownership is enforced three times: the page loads bookings through `listMine({ principal })` (query `userId: principal.id`); the actions take the principal from `requirePrincipal("bookingOwn")`, never from the client; the repository's `cancel` and `reschedule` look the booking up with `{ _id, userId: principal.id }`, so another user's booking id returns "not found" (IDOR-safe). The cutoff and status rules live in the repository; the screens only mirror them (`bookingChangeOptions`). Errors shown to the customer are mapped to friendly text (`bookingErrorMessage`), never raw codes. Cancellation and reschedule emails use the shared `notifyBookingChange` (also used by the API routes); a failed email is audited and never blocks the change. Tests: `user-bookings.test.js` (split, 24-hour boundary, friendly messages), `app/user/actions.test.js` (permission on every call, principal passed to the repository, bad ids/times rejected, friendly errors, no email on failure). Live check on a production build with a dummy customer: booked, rescheduled (Wed to Tue) and cancelled through the dashboard.

## Business settings editor (I-7, 2026-10-29)

Same write pattern with the existing permission `businessSettingsManage` (ADMIN and SUPER_ADMIN) and rate bucket `admin-settings` (20 per minute per admin); four separate Server Actions (hours, closed dates, contact, social) so each save changes one document. Validation: hours on the 15-minute grid, at least an hour long, at least one open day; closed dates real calendar dates (max 120); phone 7 to 15 digits with only phone characters; email checked; address at most 120 characters, postal code pattern; social links must be https, without credentials, and on the network's own domain (blocks `javascript:`, look-alike hosts such as `instagram.com.evil.example` and other networks). Unknown form keys are ignored. The audit log stores only which fields are set or how many days or dates changed, never phone numbers, emails, addresses or URLs. ## Barbers editor (I-17, 2026-10-29)

Same write pattern as I-15/I-16 with permission `barbersManageAll` (ADMIN and SUPER_ADMIN, already in the matrix) and rate bucket `admin-barbers` (30 per minute per admin). Specifics: the schedule written is exactly what the booking engine reads (`weeklySchedule`, one `breaks` entry per day, `daysOff` dates); times must sit on the 15-minute grid, a working day is at least one hour long, a break must be at least 15 minutes and inside working hours, days off must be real calendar dates (max 400), services must exist (rejected, not dropped), an active barber needs at least one service and one working day; unknown form keys are ignored and the slug cannot change on edit. The schedule is replaced wholesale so removing a day really removes it. No hard delete: barbers are switched off, which removes them from availability while keeping booking history. Changing hours does not move existing appointments (the screens say so). The public-profile fields (`publicProfile`, `role`, `focus`, `displayOrder`) feed the home team section only for barbers marked public. Audit: `catalog.barber.created|updated|activated|deactivated` (updates list what changed: services count, schedule, breaks, days-off count, profile flags). Tests: `barber-input` (includes a run through the real slot generator showing the lunch break removes its slot), `admin-barbers`, `actions.test.js` (denied writes nothing on all three actions, rate limit, unknown services and off-grid times rejected, typed values returned, slug ignored on edit). **Not run live with an Admin session.**

## Pricing packages editor (I-16, 2026-10-29)

## Admin write pattern and the services editor (I-15, 2026-10-29)

Pattern every admin write follows (reuse it in later units): the page calls `requireDashboardAccess("admin")`; each Server Action calls `requirePrincipal(<permission>)` itself (session, status, role, session version, TOTP enrolment, denial audit), then a per-admin rate limit (`consumeUserRateLimit`, 30 per minute for services), then strict Zod parsing of **only the known form keys** (unknown keys are ignored; the schemas are `.strict()`), then the repository write, an audit event, and `revalidateCatalog()`. Errors shown to the user are generic.

- Services editor (`/admin/services`, `/new`, `/[slug]`): permission `servicesManageAll` (ADMIN and SUPER_ADMIN). Price is entered in dollars and converted to integer cents (max $9,999.99, must be positive); duration 5 to 480 minutes; slug (create only) lowercase letters, numbers, hyphens, unique (the database unique index also enforces it); the slug and the `currency` field can never be changed by an edit. No hard delete: services are hidden instead, so booking history and barber assignments stay intact.
- Audit: `catalog.service.created`, `.updated` (with changed fields, e.g. `priceMinorUnits: 2500->3000`; names and descriptions only as "changed"), `.activated`, `.deactivated`. `appendAuditEvent` now accepts an optional `details` map of short strings (max 12 keys).
- Tests: `service-input.test.js` (price parsing, mass assignment, slug rules), `admin-services.test.js` (create, duplicate, update, not found, hide/show, audit), `actions.test.js` (permission checked on every call, denied writes nothing, rate limit stops before the database, slug argument validated, form keys ignored). **Not run live:** the editor with a real Admin session (the assistant has no admin credentials); manual steps are in `docs/TESTING.md`.

## Two-step verification for admins (I-3, 2026-10-29)

- Enrolment page `/two-factor` (guard `requireEnrolmentAccess`, pure rule `decideEnrolmentAccess`): guests go to sign-in and return; customers and suspended accounts get 404; already-enrolled admins go to their dashboard; page is `noindex`, `no-store`, disallowed in `robots.txt`.
- Flow (Better Auth `twoFactor` plugin): confirm the password (`/two-factor/enable`), receive the setup key and one-time backup codes (shown once, kept only in component state), then prove the authenticator with a first code (`/two-factor/verify-totp`); two-factor is switched on by the server only after that code. Enabling changes `twoFactorEnabled`, which bumps `sessionVersion` and invalidates the session, so the admin signs in again and meets the challenge.
- Sign-in challenge: when the response is `twoFactorRedirect`, the sign-in page shows a code step (authenticator code or a single-use backup code). No session exists until it succeeds; a successful TOTP also issues the existing step-up proof cookie. Failures use one generic message; 429 and 5xx map to their own toasts.
- Limits: `/two-factor/*` is rate limited (10 per minute per IP) on top of the plugin's account lockout (5 failed attempts, 15 minutes) and the existing failed-auth audit and burst alert.
- Tests: `two-factor-flow.test.js` (in-memory Better Auth: enrol, code needed before 2FA turns on, challenge at sign-in, wrong code refused, backup code single use, wrong password refused), `two-factor.test.js`, `dashboard-access.test.js`. **Not run live:** the enrolment pages with a real Admin (none seeded yet).

## Dashboard route guards (I-1, 2026-10-29)

Unauthorized visitors never learn that the admin areas exist (404, not a redirect or 403); only the customer area sends guests to sign-in. Decisions are a pure function (`decideDashboardAccess`) covered by a role-matrix test (3 areas x 3 roles, suspended, unknown role, stale session, TOTP). Live check on a production build: guest `/admin` and `/super-admin` 404, guest `/user` 307 to sign-in with a validated callback, customer `/user` 200, customer `/admin` and `/super-admin` 404. Admin and Super Admin paths of the guard are unit-tested only (no seeded admin existed yet).

## Seeded admin accounts (2026-10-29)
